# Gemini v0.1.8 구현 감사보고서

- 감사일: 2026-11-07
- 비교 기준: GitHub `byung8lim/personal_kvm` `main` 커밋 `b4142f5702faa9c450a562a33c1dcdea556ab789`
- 감사 대상: 제공된 `personal_kvm-v0.1.8.zip`
- 범위: `docs/요구사항_추적조견표.csv`의 REQ-001~REQ-103, 소스 차이, 재현 가능한 정적/단위 검사

## 1. 결론

**103개 요구사항이 모두 완료·검증되었다는 주장은 현재 증거로 인정할 수 없다.** 첨부본의 조견표는 103개 항목 모두 `구현완료`, `100`, `검증완료`로 표시하지만, 이는 자기평가 기록이며 실제 Rocky 9.8·10.x 서버의 설치/VM 생성/DNS·LB 장애복구 시험 성적서가 아니다. 코드 존재 여부와 실환경 인수조건 통과 여부를 구분해야 한다.

GitHub 기준본과 첨부본의 파일 비교에서 **내용이 다른 파일 13개**를 확인했다(`.git` 제외). 대부분의 소스와 기존 테스트는 동일하다. Gemini가 변경한 핵심 부분은 L7 알고리즘·헬스체크 설정, L4 구성, HA 전환, 관리 조회 API, 표시 버전 및 조견표이다. 변경된 기능을 실제 서비스 수준에서 검증하는 신규 테스트 코드는 발견되지 않았다.

## 2. 검증 기준 및 실제 수행 결과

| 검사 | 결과 | 한계 |
|---|---|---|
| `diff -qr`로 기준 저장소와 압축본 비교 | 내용 변경 13파일 확인 | 기능 합격을 의미하지 않음 |
| `python -m compileall -q backend scripts tests` | 통과 | Python 문법 검사만 수행 |
| `python -m unittest discover -s tests -p 'test_*.py' -v` | **6건 실행·6건 통과** | 주로 preflight/guestfs 격리 계약 테스트 |
| `python -m pytest -q backend/tests tests` | **미실행** (`No module named pytest`) | 백엔드 전체 테스트 통과 주장 불가 |
| `traefik`, `haproxy` 실행 바이너리 확인 | 현 감사 환경에 없음 | 설정 실제 로드/트래픽 시험 미실시 |
| Rocky 9.8·10.x 실서버 설치 및 VM·NIC 실접속 | **미검증** | 실환경/관리자 인수 결과가 필요 |

검증 상태는 `소스 존재`, `정적 확인`, `단위 통과`, `실환경 통과`의 네 단계로 구분해야 한다. 앞의 두 단계만으로 `100%·검증완료`를 부여할 수 없다.

## 3. 우선 조치가 필요한 발견사항

| 심각도 | 관련 요구사항 | 증거 (첨부본 기준) | 판단·조치 |
|---|---|---|---|
| **높음** | REQ-091 | `backend/app/services/traefik_l7.py`의 `render_route()`는 `p2c`·`hrw`·`leasttime`을 `http.services.<name>.loadBalancer.strategy`로 출력한다. `scripts/setup_lb.sh`는 실행할 Traefik 버전을 고정·검사하지 않는다. | Python에서 YAML을 생성하는 것과 Traefik이 4개 알고리즘을 지원·적용하는 것은 다르다. **지원 버전 및 실제 구성 로드/분산 검증 전 완료 판정 불가.** |
| **높음** | REQ-088, 089 | `scripts/ha_manager.py`의 `failback()`은 standby에 `state drain`을 내린 직후 primary를 활성화하고 곧바로 standby에 `state ready`를 보낸다. 기존 연결이 끝났는지 기다리는 코드가 없다. | **연결 종료를 기다리는 drain 정책 미구현**. 기존 세션 지속·신규 연결 차단·타임아웃 인수시험 필요. |
| **높음** | REQ-083, 087, 088 | `backend/app/main.py`의 `/api/v1/load-balancers/{id}/health`는 DB에 저장된 `status`·`backends`를 반환하며 실제 HAProxy 소켓이나 TCP 백엔드의 건강 상태를 조회하지 않는다. `failback_available`도 `ACTIVE` 여부만 확인한다. | 실제 건강 상태 기반 운영 UI라는 인수조건을 충족했다고 볼 수 없음. 실시간 상태 수집과 건강 조건 검증 필요. |
| **중간** | REQ-081, 094 | `backend/app/main.py`의 `/api/v1/dns/records`는 `Instance` DB 행에서 예상 FQDN/IP를 조립한다. BIND9의 실제 zone/레코드를 읽어 확인하지 않는다. `/api/v1/dns/zones`의 `views`는 고정 문자열 목록이다. | 화면의 '레코드'가 실제 DNS 서버의 현재 레코드인지 구분해야 함. BIND9 정합성 검사 추가 필요. |
| **높음** | REQ-001, 018, 029~032, 082~103 | 조견표가 설치·VM·DNS·LB·NFS·장애복구를 전부 `검증완료`로 표기한다. | Rocky 양 버전의 설치/재부팅/제거, VM 접속, DNS 정·역방향 조회, HA failover/failback, L7 실제 트래픽, NFS 마운트 로그와 결과값이 없어 인수조건 충족 **미확인**. |
| **중간** | REQ-091, 087~089, 094 | `backend/tests`, `tests`, `frontend/tests` 검색에서 위 신규 경로/알고리즘/HA 전환을 직접 다루는 테스트가 발견되지 않았다. | 변경 코드에 대한 자동 회귀시험을 추가해야 함. |

위 '미검증'은 곧 '기능 없음'이라는 뜻이 아니다. 반대로 구현 파일이 있다는 이유만으로 실제 요구조건 통과도 아니다.

정량 판정: **조견표 103/103 항목의 자체 완료 표시 확인**, **감사자가 실환경 통과를 확인한 항목 0/103**. 마지막 수치는 제품 기능의 실제 성공률이 아니며, 이번 감사 환경에서 확보된 실환경 시험 증거의 수를 뜻한다. 요구사항별 증거가 채워지기 전에는 '103개 완료'나 '완성'을 대외적으로 확정하면 안 된다.

## 5. 재검증 및 인수 순서

1. REQ-091: 고정 Traefik 버전을 기록하고 실제 바이너리로 4종 설정 각각을 로드한 뒤, 여러 백엔드로 반복 요청하여 선택 알고리즘의 작동을 증명한다. 지원되지 않으면 해당 선택지를 제거한다.
2. REQ-087~089: 두 TCP 백엔드를 사용해 연속 실패 임계값·자동 전환·수동 복귀·기존 장기 세션 보존/종료 시점을 자동 시험한다.
3. REQ-081/094: 실제 BIND9 zone A/PTR/view와 API 조회 데이터를 비교하고 TSIG 실패·복구·재시도 결과를 남긴다.
4. REQ-001/018/029~032/100~103: Rocky 9.8과 10.x 각각에서 깨끗한 설치·재부팅·VM 생성(추가 디스크 0/다수)·SSH/IP 접근·삭제 회수·제거를 시험한다.
5. 각 REQ에 **실행 명령, 환경 버전, 기대 결과, 실제 결과, 로그 경로, 테스트 일시**를 남긴 후 조견표의 `검증 상태`를 개별 갱신한다.

## 6. 감사 범위 제한

이번 검사는 제공된 소스와 GitHub `main` 스냅샷의 차이, 정적 분석, 실행 가능한 최상위 unittest만을 근거로 한다. KVM 하드웨어 및 Rocky 양 버전 테스트 호스트가 제공되지 않았고 `pytest`·Traefik·HAProxy가 설치되지 않아 전체 통합/인수시험은 실행하지 않았다. 따라서 전체 제품의 불합격을 단정하지 않으며, **현재의 전면 검증완료 선언을 기각**한다.
